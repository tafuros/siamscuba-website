5Hero-video — הרוצח השקט

הוידאו הראשי בעמוד הבית הוא ה-bottleneck היחיד שגורר את כל ה-Performance של הסייט מטה. ה-ffprobe חשף:

מאפיין ערך הקריאה
משקל 14.75 MB פי 7+ ממה שמותר ל-hero loop
אורך 1.75 שניות קצר מאוד — אז המשקל לחלוטין לא מוצדק
רזולוציה 1920×1080 (Full HD) מיותר ל-mobile hero, 1280×720 מספיק
Bitrate 18.5 Mbps זה לב הבעיה — איכות streaming, לא web
Codec h264 / 24fps ok, אבל לא efficient כמו AV1/h265

תוכנית compression (ב-Phase A)

# MP4 (h264) - תאימות אוניברסלית, ~2 MB
ffmpeg -i hero-video.mp4 -vcodec libx264 -crf 28 -preset slow \
  -vf "scale=1280:-2" -an hero-video-compressed.mp4

# WebM (vp9) - חיסכון נוסף 30-40%, ~1.4 MB
ffmpeg -i hero-video.mp4 -c:v libvpx-vp9 -crf 32 -b:v 0 \
  -vf "scale=1280:-2" -an hero-video.webm

# Poster (טעון מיידית, hero-video lazy)
ffmpeg -i hero-video.mp4 -ss 0 -frames:v 1 -vf "scale=1280:-2" hero-poster.jpg
תוצאה צפויה: 14.75 MB → ~2 MB (חיסכון 86%). LCP בית 19.1s → צפי 3–5s. Performance home 44 → ~75+. זה ה-Quick win הכי גדול במחקר.
שיפור משלים — preload + poster + lazy: להציג <img> poster ב-LCP, ולטעון את הוידאו אחרי requestIdleCallback. ככה ה-LCP יימדד על התמונה (~50KB), לא על הוידאו.

7נגישות (a11y)

axe-core CLI נכשל ב-chromedriver, אבל Lighthouse מריץ axe-core מתחת ל-hood — שאבנו את ההפרות הצרובות מתוך 5 ה-JSON-ים. כל הציונים בתחום 87–94, אבל יש 5 קטגוריות הפרות חוזרות.

הפרה home blog blog-post course fun-dive חומרה
color-contrast ✗ ✗ ✗ ✗ ✗ WCAG AA רקע/ינטר עם יחס < 4.5:1
button-name ✗ ✗ ✗ ✓ ✓ קריטי כפתורי IconButton בלי aria-label
heading-order ✗ ✗ ✓ ✗ ✓ בינוני דילוג h2→h4 או h1 כפול
landmark-one-main ✓ ✗ ✗ ✓ ✗ בינוני חסר <main> wrapper
תיקונים מהירים:
  1. color-contrast: לרוץ על palette (ב-tailwind.config) ולוודא שכל גוון על רקע שלו עם יחס ≥ 4.5:1. הכלי https://webaim.org/resources/contrastchecker/.
  2. button-name: לעבור על כל <IconButton>/<button> ב-React ולהוסיף aria-label.
  3. heading-order: לבדוק ש-Header/Page יש h1, ושכל section פותח עם h2 (לא h3/h4).
  4. landmark-one-main: לעטוף את ה-content router ב-<main role="main"> אחת.

8JSON-LD validation

שני סכמות קיימות ב-index.html: LocalBusiness ו-ItemList של 10 קורסים. ביקרתי ידנית את שניהם. תקינים מבחינה מבנית. אבל יש 4 הזדמנויות לשיפור.

סכמה מצב בעיה / הזדמנות השפעה
LocalBusiness תקין חסר aggregateRating אם יש ביקורות (TripAdvisor, Google), הוספה תפעיל star rating ב-SERP
LocalBusiness שיפור @type כללי — אפשר לצמצם ל-SportsActivityLocation או TouristAttraction תיוג ספציפי = יותר רלוונטיות בתוצאות "things to do"
ItemList (Courses) אי-התאמה offers.url מצביע על /?course=Open%20Water%20Diver אבל הראוט האמיתי הוא /open-water גוגל עלול לסמן אי-התאמה בין canonical ל-schema URL
ItemList (Courses) שיפור חסר image, inLanguage, audience ב-Course מקטין סיכויי rich result מעבר לרשימה רגילה
Article (פוסטי בלוג) חסר אין JSON-LD Article בכלל בעמוד פוסט פוסטים לא זכאים ל-rich result של אייטם חדשותי
BreadcrumbList חסר אין breadcrumb schema לדפי בלוג / קורס גוגל מציג URL pretty path ב-SERP במקום מבנה ניווט
פעולה ב-Phase A: להעביר את ה-JSON-LD מ-index.html ל-React component שמזריק לפי דף, להוסיף Article/BreadcrumbList לפוסטים ולקורסים, ולתקן את ה-offers.url להתאים לראוטים אמיתיים.

9Sitemap & broken links

14 URLs ב-sitemap.xml. כולם מחזירים HTTP 200. אין link rot. עם זאת — broken-link-checker (BLC) רץ ולא הצליח לגלות יותר מ-8 קישורים מתוך הראוט הראשי.

SPA caveat: BLC קורא את ה-HTML הסטטי שגוגל מקבל. כי האתר שלנו SPA טהור (CSR בלבד), ה-HTML הראשוני מכיל רק <div id="root"> — ה-anchor tags של מאמרי הבלוג והקורסים נוצרים על ידי React אחרי שה-JS רץ. לכן גם BLC וגם Bing/Yandex רואים shell ריק. גוגל עושה JS render אבל מקבל את התוכן באיחור גדול.

11השלב הבא — Phase A

Phase C סגור. יש לנו תמונה מלאה: הבעיה הכי גדולה היא LCP מ-hero-video, אחריו פערי SEO מבניים (per-page meta + pre-render), ואז optimization של תמונות ו-bundle. כל שלב ב-Phase A יקח 0.5-6 שעות — סה"כ ~25-35 שעות עבודה לאורך כמה sprints.

סדר עבודה מומלץ ל-Phase A:

  1. Week 1 (~5h): hero-video compression + per-page meta (פעולות 1+2). אלה לבד יקפיצו אותנו מ-Performance ממוצע 56 ל-~75+ ויפתחו את כל הראוטים ל-SEO.
  2. Week 2 (~8h): pre-render + image optimization + code splitting (פעולות 3+4+5). זה הופך את האתר לטכנולוגית-מודרני וגוגל-friendly.
  3. Week 3 (~6h): Schema enrichment + sitemap auto + a11y fixes (פעולות 6+8+9). cleanup וזכאות ל-rich results.
  4. Week 4 (~4h): hreflang + web-vitals + aggregateRating (פעולות 7+10+11). polish.

אחרי Phase A: הרצה חוזרת של Lighthouse על אותם 5 ראוטים כדי למדוד את ה-delta. היעד: כל הראוטים Performance ≥ 75, LCP ≤ 4s, A11y ≥ 95.
